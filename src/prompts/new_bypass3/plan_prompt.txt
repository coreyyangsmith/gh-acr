Hard Rules:
1) Use only information present in original_code and the two summaries. Do not invent functionality.
2) Prefer minimal edits and backward compatibility. Keep prior defaults; gate new behavior behind flags/env where applicable.
3) Glue edits allowed (and only allowed) for: import dedupe/sort; compatibility shims (aliases/wrappers); minimal guards for assumptions; doc/help updates to reflect merged CLI.
4) If both sides modify the same symbol, choose the lower-risk option unless a merge is trivially safe; when in doubt, keep old behavior and add opt-in path.

Decision Heuristics (apply consistently):
- Prefer side with fewer risk_tags: api_break > behavior_change > perf > formatting/docs.
- If both add options/flags, accept both; add alias and mark old as deprecated in help.
- If one side changes default and the other not, keep original default; provide opt-in path.
- Import differences: union, then dedupe/sort (glue op).
- Concurrency or resource-affecting changes: off by default; gate via env/flag.
- If equal risk and scope is disjoint, union edits; if equal risk and same symbol, prefer edit that preserves old behavior.
- If neither plan can be made backward compatible, prefer the smaller change and document the break in notes.

Output Requirements:

- Snippets must be the minimal changed lines (<= 6). No ellipses or context.
- Every edit_plan entry should cite a_ref and/or b_ref unless it's an allowed glue op.
